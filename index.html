IT configures once. Humans and AI build freely within authorized boundaries.

An open-source, self-hosted platform on which an enterprise's employees and their AI coding agents build, deploy and run internal applications against shared, IT-governed infrastructure. Think PocketBase for the enterprise, built for the AI coding era.

§ 1 · Who it is for

One environment, set up by IT, built on by everyone.

Platform administrators

Install it once: one image and one Compose file start the platform beside a bundled Postgres 18 and a reverse proxy that terminates TLS with your wildcard certificate. People sign in with your company's identity provider (OIDC); their Groups come from it.

Installing with Compose →

Builders

An employee who creates and deploys an Application, normally by directing a coding agent. No authentication to write, no credentials to manage, no infrastructure to provision: the platform supplies them.

Getting started →

Coding agents

AI generates application logic; the platform supplies the governed environment. Agents use the tool's commands, each with --json, and the project's AGENTS.md tells them how to work in it.

§ 2 · How it works

From nothing to an Application open in a browser.

  1. Make a project

    vibe new makes a project from the template. vibe check says whether it will deploy, with each problem and its fix.

    vibe new hello
cd hello
npm install
vibe check

  2. Run it on your computer

    vibe dev serves the Application to your browser as a test User you choose, with test rows, beside a private Postgres. Open http://hello.localhost:7480/.

    vibe dev
vibe request --as outsider /

  3. Deploy it

    vibe deploy builds the Application on your computer from its last commit and sends it as a new Version, which goes live at https://hello.vibe.example.com/.

    git add --all
git commit -m "The first version"
vibe deploy

  4. Share it

    It opens for its Contributors alone until one of them shares it with people, Groups or everyone, with vibe share or on the Dashboard.

    vibe share hello --email colleague@example.com
vibe share hello --group engineering
vibe share hello --everyone

§ 3 · Governed by default

The context is the platform's. The records are the platform's.

Every operation an Application makes carries a Trusted context: which User, which Application, which request. Application code receives it and cannot construct one. An Application reads and writes a shared database only as its Grants allow, as the person who uses it.

Every operation of an Application on a shared database is in the Operation log, and every row it changes in its own database is in the Change history, with who did it and through which Application.

§ 4 · In v0.1.3

What works, and what does not yet.

New since 0.1.2

  • The pages say each thing once. The Dashboard's list no longer repeats the Contributors and every Resource on each Application; a refusal, the sign-out page and the pages for an address that does not exist no longer say under their title what the title said.
  • Marks before words. A state is a mark with a colour and a shape: a lock for an Application that is not shared with you, a check, a cross, a warning.
  • The list first, the rest one step away. An Application in the Dashboard's list shows its name, its description, "Open" and at most one mark when a part of it will not work for you ("Missing access", "Not set up", "Access unknown").
  • Smaller things. A page of the sign-in address says which installation it is.

Works

  • Installing. One image and one Compose file start the platform beside a bundled Postgres 18 and a reverse proxy that terminates TLS with your wildcard certificate.
  • Signing in. People sign in with your company's identity provider (OIDC).
  • Making an Application. vibe new makes a project from the template.
  • Shared databases. A Builder lists the Resources (vibe resources) and pulls one's structure into the project as a typed definition (vibe pull).
  • Running it on your computer. vibe dev serves the Application to your browser as a test User you choose, with test rows, beside a private Postgres.
  • Deploying. vibe deploy builds the Application on your computer and sends it as a new Version, which goes live at https://<name>.<domain>/.
  • Sharing. Contributors may change and deploy an Application.
  • The Dashboard lists the Applications you contribute to and those shared with you, says what of each will not work for you, and lets a Contributor share one.
  • Records. Every operation of an Application on a shared database is in the Operation log, and every row it changes in its own database is in the Change history, with who did it and through which Application.

Not yet

  • Shared databases' credentials are kept in the platform database without encryption.
  • There are no limits per request yet: one Application can use as much CPU time, memory and time as it likes, and so slow down the others.
  • The runtime that runs Applications is not yet closed against every way an Application could stop the whole program.
  • An Application cannot call services outside the platform (fetch to the internet).
  • An Application cannot serve static files: its pages are strings in its code.
  • An Application cannot be deleted.
  • An Application's source is not kept on the platform: it stays in your own Git repository.
  • Platform administrators cannot yet see every Application, disable one, or read the Operation log with the tool.
  • There is no report of Applications built against an older structure of a shared database that has changed.
  • Coding agents use the tool's commands; there is no MCP interface yet.
  • The tool is not on npm, and there is no Windows build.
  • After signing in to an Application, its address in the browser's address bar keeps the sign-in's state and code (issue #72).
  • Reviews found smaller things still to be done in the identity and capture of operations, in the Application's own database, in the SDK's values, and in long histories.
