# Instructions for the coding agent

This folder is one Application for the company's internal platform. The person you work for is the Builder: an employee who describes what they need, often not a programmer. You build the Application, try it, and deploy it with the `vm` command. Talk to the Builder in plain words; they do not need to learn the terms below.

## What an Application is

- A TypeScript web app. `src/index.ts` exports `defineApp(manifest, { fetch(request, ctx) { ... } })`; `fetch` returns a `Response` (HTML or JSON). Every route requires sign-in, so `ctx.user()` is always the signed-in employee (the User).
- It reaches company data only through `ctx`. No connection strings, passwords, API keys or direct network calls to company systems, and no Node APIs (`fs`, `net`, `child_process`): it runs in a Workers-style runtime.
  - `ctx.user().db("<name>")`: a shared company database (a Resource), acting as the User.
  - `ctx.user().ownDb()`: the Application's own database, acting as the User.
  - `ctx.app().ownDb()`: the own database, acting as the Application itself. It acts as itself only in its own database, never in a shared one.
- Every database handle is a Drizzle database (`drizzle-orm`), typed with that database's tables. Query with Drizzle (`db.select().from(t).where(eq(t.id, 1))`, `db.insert(t).values(...)`, `db.transaction(...)`), not raw SQL. Type a handler's context as `Ctx` from `manifest.ts`.
- `manifest.ts` gives the Application's `name` (it becomes the address), a one-sentence `description`, and every Resource it uses, at `"read"` or `"write"`. The Application reaches only what the manifest declares. Keep it a plain literal: no variables, imports or spreads.
- `src/db/schema.ts` defines the own database's tables in Drizzle. `migrations/` is generated from it by `npx vm db generate`; never write or edit migrations by hand.
- `resources/<name>/` is generated by `npx vm resources pull <name>`. Read it, import its tables from `resources/<name>/schema.ts`, never edit it.

## Commands

Run them from this folder with `npx vm ...`. Each has `--help` and `--json`.

| Command | What it does |
|---|---|
| `npx vm whoami` | who the Builder is, and their Groups |
| `npx vm apps list` / `apps show <name>` | existing Applications the Builder contributes to or can open |
| `npx vm resources list` | every company Resource, the Builder's access to it, and whom to ask |
| `npx vm resources pull <name>` | writes `resources/<name>/` with that Resource's tables |
| `npx vm db generate` | writes a migration after you change `src/db/schema.ts` |
| `npx vm check` | checks the manifest, Resources, migrations and types |
| `npx vm dev request --as <user> GET /path` | runs one request locally as a test User and prints the response |
| `npx vm dev` | runs the Application locally for a browser (keeps running) |
| `npx vm deploy` | deploys the committed project as a new Version |

## How to work

1. **Look for an existing Application first.** Run `npx vm apps list`. If one already does what the Builder asks, tell them its name and address and ask whether they still want a new one. If one comes close, say so before building.
2. **Find the data.** Run `npx vm resources list` and choose Resources by their description. Pull each one you need and read its `resources/<name>/schema.ts` to learn the tables. Declare it in `manifest.ts`, at `"read"` unless the Application must change rows there.
3. **Keep the Application's own data in its own database.** Anything the Application records itself (notes, acknowledgements, preferences) goes in `src/db/schema.ts`, then `npx vm db generate`. You cannot add tables or columns to a shared Resource; store the extra data in the own database and relate it in code (there are no joins across databases).
4. **Write the handlers**, try them locally, run `npx vm check`, commit, deploy.

## Access belongs to people: a refusal for a missing Grant is not a bug

A Grant gives a directory Group an access level on a Resource: `structure` (can see its tables, no rows), `read`, or `write`. When anyone uses the Application, each operation on a Resource is allowed only if the manifest declares the Resource at that level **and** one of the User's Groups holds a Grant for it. The same Application shows different data to different people.

A refused operation throws `Refused` (import it from `@vm/sdk`), with `refusal.reason` and a `fix` sentence. If you don't catch it, the User gets a 403.

- `not-declared` or `declared-lower`: fix `manifest.ts`.
- `no-grant`: the User lacks access. This is working as intended. Do not work around it: no other Resource used as a substitute, no copying of data into the own database to get past it, no hard-coded or mocked data. Where some Users will lack access, catch `Refused` and show them a clear message, and tell the Builder who needs which Grant.

**If `npx vm resources pull` is refused because the Builder holds no Grant, stop and tell the Builder.** Say which Resource the request needs, what for, and whom to ask (the refusal names them). Getting access means a person adds the Builder to a Group; you cannot do it. Do not invent the Resource's tables, mock its data, or quietly drop the feature that needs it. If the rest of the request is useful without it, ask the Builder whether to build that part now.

If the Builder holds only `structure` on a Resource, you can build against it, but the Builder and everyone else without a `read` Grant will be refused its rows. Tell the Builder who will be able to use that part before building it.

## Migrations that destroy data: ask the Builder

If `npx vm db generate` or `npx vm deploy` stops because a migration destroys data (drops a table or column, changes a column's type), do not add `--allow-data-loss` on your own. Tell the Builder exactly what would be lost and ask. Deploying an older Version later does not bring the data back. To rename a column or table, add the new one, copy the values, then remove the old one.

## Trying it locally

You cannot click in a browser, so use:

```
npx vm dev request --as <test user> <METHOD> <path> [--data '<json>'] [--header "Name: value"]
```

It runs the Application on this machine and prints the response. Locally:

- the own database has every migration applied, and its rows persist between runs (`npx vm dev --reset` clears them);
- each pulled Resource is a local stand-in, filled from `seed/<name>.sql` with test rows, never real company data. Edit the seed file to cover your cases;
- test Users, their Groups and those Groups' Grants are in `vm.dev.json`. Pulling a Resource adds the Grants the Builder's own Groups hold.

The rules are the same as after deploying. Add a test User who holds no Grant (for example `{ "id": "outsider", "displayName": "Outsider", "groups": [] }`) and check what they get. `npx vm dev` serves the Application at `http://<name>.localhost:8787` for the Builder to open.

## Deploying

Set a real `name` and `description` in `manifest.ts`, run `npx vm check`, commit, then `npx vm deploy`. It pulls each Resource's structure again, checks everything, and prints the Version and the address. Give the Builder the address. A new Application is visible only to its Contributors until it is shared from the Dashboard.
