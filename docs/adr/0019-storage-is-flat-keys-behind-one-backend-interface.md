# Storage is a Resource of flat keys behind one backend interface; the first backend is a directory reached only beneath its own descriptor

The product owner pulled Storage forward on 2026-11-21: "file system, local file for now and s3 for later, make sure your mount, your user access rule etc.. works". The ticket "Storage: a shared, named file Resource, on a mounted directory now and S3 later" reads that as a second kind of Resource (`CONTEXT.md`: named, registered by a Platform administrator, reached by its name alone through the SDK, as the User, decided per operation by Grants and the Version's Declared access, every operation in the Operation log; ADR 0003, ADR 0005, ADR 0014). This ADR records what the program's interface to a place of files is, so that S3 is a second backend and not a second feature, and how the first backend, a directory mounted into the platform's container, keeps every file inside it.

What already exists and constrains it (each read in this session; "contract" is `blackbox/CONTRACT.md`, "code" is the source under `crates/` and `vendor/`):

- An Application reaches the host only through `env.VM.invoke(operation, args)`, answered `{ ok }`, `{ refused: { refusal, fix } }` or `{ error: { kind, ... } }` (contract, "The raw host interface"). The vendored runtime reads `args` with `JSON.stringify` and hands the host a `serde_json::Value`; the answer goes back as JSON (code: `vendor/openworkers-runtime-v8/src/runtime/bindings/fetch.rs`, the patched `setup_invoke`; `openworkers-core` `InvokeResult` is `Value(serde_json::Value) | Error(String)`). On that one binding there is no binary or streaming path; the body section below first took that for the whole core, and the research of 2026-11-22 found it was not ("Bodies: a handle and a stream").
- A context's heap is 64 MB, a request may use 2,000 ms of CPU and 30 s in all, and a body an Application's code itself makes is at most 8 MiB (code: `crates/vibe/src/runner/mod.rs` `Limits::default`). The 30 s is also in the contract; the others are code only. A request body given to an Application was at most 1 MiB in `vibe serve` before this ticket, 8 MiB and 64 KiB after its stage 1 (code: `crates/vibe/src/main.rs` `max_request_body_bytes`), and is 5 GiB and 64 KiB with the body rework below ("Bodies: a handle and a stream").
- Operations are decided by `authz::decide`, a pure function of the request in flight, the actor, the own database, the Groups, the declared level, whether the Resource is registered, its Grants and the level needed (contract, "Lower seam"; code, `crates/authz/src/lib.rs`). It knows nothing of a Resource's kind.
- An Operation log entry has `operation`, `statement` (text without values), `rows`, `outcome`, `reason`, `error` and the rest (contract, "The Operation log" and later sections). A non-SQL operation already writes its own text into `statement`: `history "<schema>"."<table>"` (contract, "Reading: the operation `history`").
- Every operation runs as a task owned by the Operation gateway, at most 256 at once, waiting at most 5 s for a permit (code: `crates/vibe/src/gateway/mod.rs`, `OPERATIONS_AT_ONCE`, `PERMIT_WAIT`). The workspace's `tokio` has no `fs` feature, and `rustix` 1 with `fs` is already a dependency (code: root `Cargo.toml`). `unicode-normalization` 0.1.26 is already in the lock file (code: `Cargo.lock`).
- The image runs as `65532:65532` with a read-only root filesystem, every capability dropped and `no-new-privileges`; the Compose file mounts only `deploy/ca/` read-only (contract, "Installing"; code: `Dockerfile`, `deploy/compose.yaml`).
- A Resource's connection is stored as JSON in `resources.connection`, not yet encrypted; the ticket "Resources and Grants in full" seals it under `VIBE_SECRET_KEY` (code: `crates/vibe/src/resources.rs`, `mod sealed`; ADR 0018).

## The decision

### One interface, five operations, flat keys

The program reaches a place of files through one Rust trait, `Backend`, with five operations, each on a **key**: a string that names one file of the Resource. There are no directories in the interface. `/` is a separator in a key and nothing more: a "folder" is the set of keys that begin with `<folder>/`, it exists exactly while one of them exists, and it is never created, listed as an object, or deleted on its own. This is S3's model (its user guide: "a flat structure ... There is no hierarchy of subbuckets or subfolders"), and the one a directory can keep without the Application ever learning which it is.

| Operation | Needs | Semantics every backend keeps |
|---|---|---|
| `head(key)` | `read` | The file's metadata, or *none* when no file has that key. |
| `get(key)` | `read` | The file's metadata and a stream of its bytes, or *none*. A get answers one whole version of the file: never part of one write and part of another. A file larger than the file bound is not opened: it fails `limit: bytes` (its `head` still answers). |
| `put(key, body, content_type?)` | `write` | Creates the file or **replaces it whole**. Unconditional: the last put to finish wins. Atomic: a reader sees the file as before or as after, never in part; a put that fails leaves the file as before. The body is a stream, a string or bytes, written to staging as it arrives; nothing lands until it has ended cleanly. Answers the new metadata once the file has landed. |
| `delete(key)` | `write` | Removes the file if there is one; answers the same whether there was or not (S3's `DeleteObject` cannot tell without a second request). Removing a folder's last file makes the folder disappear. |
| `list(prefix, delimiter?, start_after?, limit)` | `read` | Keys that begin with `prefix`, **in the byte order of their UTF-8**, at most `limit` (1 to 1,000), after `start_after`. With delimiter `/`, keys that hold a `/` after the prefix are rolled up into one *folder* each (S3's `CommonPrefixes`), sorted with the files, each counting once against `limit`. The answer says where the next page starts (an opaque cursor), or that there is none. |

**Metadata kept**: the size in bytes, the content type, and the time of the last change, to the second. Nothing else in this ticket: no ETag, no user metadata, no versions. Seconds, because S3 gives `Last-Modified` in seconds on `HEAD` and `GET` (its list gives milliseconds, but one backend cannot answer two precisions for the same file).

**Not in this interface, on purpose**: conditional writes (create only if absent, replace only if unchanged), renaming, copying, ranges, appending. A copy is possible at the body level since the body became a stream (`put(k2, (await get(k1)).body)`) but is not one atomic server-side operation. S3 now has conditional `PutObject` (`If-None-Match`, `If-Match`; its user guide, "Add preconditions to S3 operations with conditional requests", fetched this session) and a directory can do "only if absent" with `renameat2(RENAME_NOREPLACE)` (verified, below), so "create only if absent" is the first addition when an Application needs it; it is left out until one does, so that the first S3 backend need not depend on a store that speaks it (other S3-compatible stores may not: not verified).

**One file and one folder of the same name cannot both exist.** A directory cannot hold `a` as a file and `a/b` beneath it; S3 can. The interface takes the directory's rule: a put of `a/b` while `a` is a file, or of `a` while a key begins with `a/`, fails `key-conflict` and writes nothing. The S3 backend will check with one `HEAD` and one `list(prefix, limit 1)` before its put; that check is not atomic on S3, so two puts racing can leave both there, and S3's own list then shows both. This is the one place the two backends may differ, and the ADR of the S3 backend has to state it.

### The key

A key is checked by the host, the same for every backend, before anything reaches a backend. It is the intersection of what S3 takes (any UTF-8, at most 1,024 bytes, case-sensitive: its user guide, "Naming Amazon S3 objects", fetched this session) and what a file system on Linux and macOS takes (a name of at most 255 bytes, no NUL, no `/` inside a name; `.` and `..` are not names), with what is dangerous to a person or a program reading it taken out:

- 1 to 1,024 bytes of UTF-8, in Unicode **NFC**. A key not in NFC is refused, never normalised: macOS file systems compare names regardless of normalisation and S3 compares bytes, so only one form can mean the same file on both (checked with `unicode_normalization::is_nfc`, below).
- Segments are separated by `/`; at most 64 segments, each 1 to 255 bytes. No empty segment: no leading `/` (so no absolute path), no trailing `/`, no `//`.
- No segment is `.` or `..` (S3's guide warns against them too, "Period-only path segments").
- No character that is a control (U+0000 to U+001F, U+007F to U+009F), none of the bidirectional marks the tool already escapes (U+061C, U+200E, U+200F, U+202A to U+202E, U+2066 to U+2069), and no `\` (the separator of the Windows local loop to come). Everything else, spaces, `#`, `&`, `%`, `[`, non-Latin scripts, is taken: S3's "characters to avoid" are about clients that build URLs by hand, and the platform builds none for a key.
- No segment begins with `.vibe-`, in any letter case: those names are the platform's own on disk (below), and on a disk that does not tell letter case apart (macOS's default, where the local loop runs) `.VIBE-resource` is the marker itself.
- Case is kept and matters, as on S3 and on Linux. On a case-insensitive disk (macOS, in the local loop) `Report.pdf` and `report.pdf` are one file: a difference of the local loop, stated where it is described.

A key that breaks a rule is an error of the operation (`invalid-key`, naming the rule), decided **after** the Authorization decision, as the statement check is for SQL (contract, "Write access": "who is allowed (a refusal) first, then ... the statement check"), and it has its Operation log entry: an attempt with `../` in it is something IT wants to see.

### The directory backend: nothing escapes

A Storage Resource on this backend is a directory **beneath the installation's storage root** (`vibe serve --storage-root <dir>`, `/var/lib/vibe/storage` in the image). At registration the host checks it: it is there, is a directory, is beneath the root, no component between the root and it is a symbolic link, it is writable by the program (shown by creating and removing a file, not by `access(2)`), it keeps extended attributes (shown the same way), and it is neither the directory of another Resource nor inside one nor holds one. Then it writes a marker `.vibe-resource` holding the Resource's name and makes `.vibe-staging/`.

When a Resource is loaded (at start, at registration) the host opens its directory and **keeps the descriptor**. Every operation is relative to that descriptor and never to a path string. Each opening, at start too, reaches the directory as the registration did: from the storage root the program was started with, one component at a time, following no link, so what the registration checked holds for as long as the Resource is used and not only on the day it was registered (a Resource whose directory is not beneath the root the program now has is not used). A directory that cannot be opened so, or whose marker is missing or names another Resource (a mount forgotten after an upgrade, the wrong disk), makes the Resource's operations fail `unavailable`, never write into whatever is there; the host tries to open it again at most every 10 seconds.

The path is used for nothing but opening. While the program runs it looks, at most every 10 seconds and at an operation, whether the path still names the directory it holds (one `stat`); when it does not (moved away, removed, another disk mounted at its place) it lets go of the descriptor and opens again through the same checks. Without this a directory removed and made again stayed unusable until a restart, and a mount that came back was not picked up (found at the review of the first build). An operation never follows the path: only the descriptor.

At start the directories are opened together and waited for 3 seconds in all; one whose file system does not answer (a network mount whose server is away) is left unavailable, holds one file thread until it answers, and does not keep the program from starting.

A key is reached **one segment at a time**: `openat(dir, segment, O_NOFOLLOW | O_DIRECTORY | O_CLOEXEC)` for each folder, each relative to the descriptor before it, and the last with `O_NOFOLLOW | O_NONBLOCK | O_CLOEXEC`, then `fstat`: only a regular file is a file. Because a key has no `.`, `..` or empty segment and each step is taken from a descriptor already held, nothing can lead outside: a symbolic link anywhere on the way is refused by `O_NOFOLLOW` (`ELOOP` for the last segment, `ENOTDIR` for a folder, which `fstatat(AT_SYMLINK_NOFOLLOW)` then tells apart from a file in the way), a FIFO or device is opened without blocking and refused by `fstat`, and a folder swapped for a link by someone on the host between two steps is refused at the next step. A folder on another file system than the Resource's directory (a mount inside it) is refused too, by comparing `st_dev`: a put's rename must stay on one file system. Each of these answers the operation `not-reachable`, saying which (`link`, `not-a-file`, `other-filesystem`), and `list` passes such entries over. All of it is `rustix::fs` (`openat`, `fstat`, `statat`, `mkdirat`, `renameat`, `unlinkat`, `fsync`, `fgetxattr`, `fsetxattr`, `Dir`), safe Rust: rule 1 holds.

**Why not `openat2(RESOLVE_BENEATH | RESOLVE_NO_SYMLINKS)` alone.** It does the same in one call on Linux 5.6 and later, and works under Docker 29.2.1's default seccomp profile (verified, below). But the same backend serves the local loop on Builders' Macs, where there is no `openat2`, and Windows later; a fallback for kernels without it (or a seccomp profile that answers `ENOSYS` or `EPERM`) would be the segment walk anyway. One path, tested everywhere, is the decision. `openat2` may be added later as a second guard on Linux if the walk's cost is ever measured to matter (one `openat` per segment, at most 64).

**Hard links are not refused.** A hard link planted on the host to a file outside would be read as a file of the Resource. Making one needs write access to the Resource's directory and, with `fs.protected_hardlinks = 1` (the default, 1 on this machine), ownership of the target or read and write access to it: only someone who could already read the target. Refusing files whose link count is above 1 was considered and rejected: backups by hard-linked snapshots (`rsnapshot`, `cp -al`) would make every file of the Resource unreachable.

**A put is atomic and durable.** The body is written into a new file in `<resource>/.vibe-staging/` (`O_CREAT | O_EXCL`, mode `0640`, a random name) as it arrives, a chunk at a time as jobs on the file threads; then the content type is set, the file `fsync`ed, the key's folders that are missing made (`mkdirat`, mode `0750`, each then opened again with `O_NOFOLLOW`), the file `renameat`ed onto the key, and the folder `fsync`ed. `rename` within one file system replaces the name atomically: a reader that opened the old file keeps reading the old file whole, and a later open finds the new one (verified, below). A rename onto a symbolic link replaces the link, not what it points at (verified); the host refuses it before, as `not-reachable` `link`, and the rename only makes the race harmless. A put that fails removes its staging file; what a crash leaves in `.vibe-staging/` is removed when the Resource is next loaded. A delete `unlinkat`s the file, then removes each folder of the key that is now empty, deepest first, stopping at the first that is not (`ENOTEMPTY`), and `fsync`s what it changed.

**The content type** is kept in the file's extended attribute `user.vibe.content-type` (set on the staging file's descriptor, so it is renamed with the file; verified on ext4, below). A file without it (placed by someone on the host) has the type its name's extension gives in a small fixed table of the program's, else `application/octet-stream`. Considered: a sidecar file per file (twice the files, visible to everyone on the host, out of step after a host-side `mv`), and the extension alone (loses what the Application said, and S3 keeps what it was told). Extended attributes are why registration checks that the directory keeps them: an NFS export or a file system without `user.*` attributes is refused at registration, saying so, instead of losing content types silently.

**A page may be short.** A list answers at most `limit` items and may answer fewer, even none, with a cursor: it stops looking after 5 seconds and hands back where it got to, and the cursor is the last name it passed, answered or not. S3's `ListObjectsV2` may do the same (fewer than `max-keys` with `IsTruncated`), so a caller that pages until the cursor is null is right for both backends. Found at the review: with the cursor at the last key *answered*, a folder of 20,000 names that are never answered (empty folders made on the host) could not be paged past at all.

**list** reads one folder at a time (`Dir` on a descriptor reached as above), skips every name that is not a valid key segment (the `.vibe-` names among them), and walks depth-first with each folder's entries sorted by their bytes, **a folder's name taken as `name/`**. That gives exactly the byte order of whole keys that S3 gives: a plain sort of names does not (`a-b` sorts before `a/c` because `-` is below `/`). Checked in this session against 20,000 random trees (below). The cursor is the last key answered; the next page re-descends to it. A folder with very many entries is read whole at every page that passes through it: the cost of a page is the size of the folders it walks, not the page; it is bounded by the operation's time (10 s, then `limit: time`), and measured when the ticket is built.

### Off the async workers, bounded

File I/O blocks. It runs on a pool of the backend's own: **8 threads**, fed by a `std::sync::mpsc::sync_channel` of **64** jobs (rule 3). An operation that cannot hand its job over within the gateway's `PERMIT_WAIT` (5 s) fails `unavailable` and touches nothing. Each operation has **10 seconds** from the moment it is decided (rule 7), as a statement has; past them the Application is answered `limit: time` and the Operation log entry is completed `failed` — a put is the exception: it is part of its request and ends with it, and one write and the landing each have their own 10-second wait (past one, `limit: time`, today's kind for an operation past its time), so that a body may take longer than 10 seconds' worth of disk and still land within its request; a source that stalls is bounded by the request's own end, and by the request body's 10-seconds-without-a-byte rule when the source is the request's body. A chunk read or written is one job. A system call cannot be cancelled: the thread finishes what it was doing (a chunk write in flight ends, but a put given up never takes its landing step, so a put then lands or is removed, as above, and its entry already says `failed`, which is the case "a write whose answer is lost" names for the database), and the pool's bound means a disk that hangs takes 8 threads and no more, after which operations fail `unavailable` at once. The pool and its threads are owned by the backend and joined when the program stops (rule 6). Not `tokio::task::spawn_blocking`: its queue has no bound.

### Bodies: a handle and a stream

The product owner decided on 2026-11-22, and called it not negotiable: **a file never enters the Application's JavaScript whole. The SDK gives a handle whose body is a stream, as Cloudflare R2 does; bytes move between the host and the request or response natively and enter the JavaScript heap only when the code asks for them.** The body path of stage 1 is reworked before the rest of the ticket. Everything else of stage 1 stands: the keys, who is allowed, registration, the directory backend's walk, the Operation log's shape, `list`, the storage root, unavailable directories.

Stage 1 had a body cross inside the JSON of one host call, as base64 text, "because that is the only path the execution core has today" (this ADR, as first written). That claim was true only of the invoke binding — the one operation kind our host exposes — and the research for this change found the core has nearly everything else already (read from source; the reports of 2026-11-22, the vendored runtime and the host):

- The runtime has **host-fed native streams** (`StreamManager`, `__createNativeStream`): a stream id becomes a `ReadableStream` whose `pull` asks the host for the next chunk, backpressured by a bounded channel, one allocation a chunk, the bytes entering the heap only when the code reads them.
- **A native stream given as a `Response`'s body is forwarded in Rust without passing through JavaScript** (`stream_body.js`, `read_response_object`); the guest's event even ends at once and the host takes the receiver.
- The runtime **accepts a streamed request body** (`RequestBody::Stream`, `pump_request_body`), fed by the host as the guest reads it.
- **JavaScript can write binary chunks to the host with backpressure** (`__responseStreamCreate` / `__responseStreamWrite`, the channel refusing when full), and the host can take the reading half (`take_receiver`).
- The upstream storage binding even demonstrates the handle shape — an answer carrying a `streamId` that the guest turns into a `Response` — though that binding is not exposed to Applications here (ADR 0002).

What the host must build is therefore not a new crossing but the wiring at both ends: **a streamed request body in** (ingress no longer collects it; sign-in, sharing and every other check still come before the first byte is read), **a streamed response body out** (the runner and ingress no longer collect it; the server answers with a body that streams), and **a handle from a host call** (`storage.get`'s answer naming a stream the host feeds; `storage.put`'s body taking one). The small changes this needs in the vendored runtime are at most three, to be recorded in `vendor/VENDORED.md` by the implementation: the **invoke answer naming a stream** (an id in the answer's JSON, turned into a `ReadableStream` by the existing `__createNativeStream` helper — extending `InvokeResult` itself would be a change to `openworkers-core`, which we do not vendor, and a larger decision than a runtime patch); the **runner learning which host-fed stream became the response's body and whether the code read it**, so the host can send that body itself, go on sending it after the code has ended, and set `content-length` to the length it opened the body with; and **a bound on the size of a chunk and on the number of streams the code opens** (the natives have neither today; read from source).

The interfaces. Through the SDK, `get(key)` resolves to `FileInfo` plus `body: ReadableStream<Uint8Array>` (fed by the host as it is read, chunks of at most 64 KiB), `bodyUsed`, and `arrayBuffer()`, `bytes()`, `text()` and `json()`, each reading the stream to its end once — a second use rejects as a `Response`'s does; `text()` is no longer synchronous. `put(key, body)` takes a stream, a string, bytes or a `Blob`, and resolves once the file has landed whole; a stream that is locked or already read is a `TypeError` before any host call. Through the raw interface base64 is gone: `storage.get` answers a `body` that is a `ReadableStream` of bytes, `storage.put` takes one (or a string, or bytes), and a value that is none of these is an error of the call, as a wrong type is today.

What the shape is, and why:

- **A get opens the file and answers its metadata and a stream of its bytes.** The Operation log entry is finished when the file is open; it does not say how much of the body was read afterwards. The body is the file as it was when it was opened — a put or a delete of the same key meanwhile changes nothing of it, because a rename never changes what an open descriptor reads — and it ends after exactly `size` bytes; a file found shorter (someone on the host changed it in place) fails the stream, never ended as if whole. A body given back unread as the response's body (`new Response(file.body, …)`) is **sent by the host itself**: the bytes never enter the Application's memory, the sending goes on after the code has ended (the request's deadline and CPU limit bound the code, not the sending), and the platform sets `content-length` to the length it opened the body with, whatever the Application set. The same holds for any body the host itself feeds and the code did not read — the request's own body given back, for one. A body being sent is ended early, the connection closed without a clean end (so the client can tell, by `content-length`), when the client takes no byte for 30 seconds, when the client goes away, when the Application is disabled (within the second the contract gives a disable), or when the program stops; the limit on one connection's life does not cut it. A Grant withdrawn while a body is being sent does not cut it either: the decision was taken at the get, as an operation under way is not cut.
- **A put takes a stream (or a string, or bytes) and writes it to the staging file as it arrives; nothing lands until the body has ended cleanly.** A body that fails — the kind `body-failed`: a stream of the code's own erroring or cancelled, or the request's body failing while the put reads it (past its bound, no byte for 10 seconds, the client gone) — a request that ends first (its deadline, a disable), a body past the bound, a full disk: nothing lands, nothing is left in staging, and a file already at the key is untouched. A put under way when its request ends is given up as a statement still running then is cancelled — its Operation log entry `failed` with `error` `request-ended`, or `application-disabled` at a disable — and lands nothing. The landing itself is as stage 1 (fsync, rename, folders). A put is part of its request and ends with it — nothing of it goes on after the code has ended; within that one write and the landing each have 10 seconds of their own, past which `limit: time`, today's kind for an operation past its time, while a stalled source is bounded by the request's own end. The request's own body given unread to a put (`storage.put(key, request.body)`) goes from the socket to the file without entering the Application's memory; so does another file's body (`put(k2, (await get(k1)).body)`) — a copy, but not one atomic server-side operation.
- **The bounds.** A file is at most **5 GiB** (5,368,709,120 bytes: the most one S3 put takes, which the S3 backend will have anyway), and a request body at most **5 GiB and 64 KiB**, in `vibe serve` and in the local run alike; a request whose `content-length` is over it is answered `413` before the code runs, as today, and a body with no stated length that passes it fails the stream the code is reading — the request was given to the code, so it has its log entry and records, whatever the platform answers next. A put checks the file bound before a byte is read when the body's length is known (a string, bytes, the request's own body when it stated a `content-length`), and while the body is written when it is a stream. Chunks are at most **64 KiB**. **16 open bodies a request, 512 in the program** (a body being read, written or sent holds one); **16 streams of the code's own a request**; and about **4 MiB of the program's memory for one open body**, so a hostile Application that opens every stream it may and writes the largest chunks it can does not make the program's memory grow by more than 128 MiB a request in flight. The 8 MiB call bound, the base64 text bound, the 256 MiB budget of bodies at once, and "a put with no room is answered `unavailable` at once" all go: each existed only because a body was one value inside one call.

Two things are left as they were, on purpose. A body the Application's code itself makes — a `ReadableStream` of its own, a `TransformStream`'s output, a string, bytes — is still answered whole and at most 8 MiB, within the request's time: streaming a generated response is its own decision. And a body the code has begun to read and then gives back is the same: the code has taken the stream into its own hands, and what it hands back is no longer a body the host can vouch to forward as the file it opened — the buffered path, which the code's own reading has already paid for, is the honest one.

### Registration: kind, backend, location

`POST /v1/resources` takes `"kind": "storage"` and, in place of `connection`, `"location": { "backend": "directory", "directory": "<absolute path in the container>" }`. The platform database records the kind in `resources.kind` and the location in the column that holds a database's connection today, in the form the `sealed` module writes. A directory needs no credential. The S3 backend will take `{ "backend": "s3", "endpoint", "region", "bucket", "prefix", "access_key_id", "secret_access_key" }`; its keys are a credential and are sealed under `VIBE_SECRET_KEY` with the rest of the Resources' credentials, as the ticket "Resources and Grants in full" does (ADR 0018). Nothing of a location is in any answer, log record or error message, as for a connection.

### The access rule and the kind

A Grant on a Storage Resource is `read` or `write`; `structure` has no meaning there and is refused. `head`, `get` and `list` need `read`; `put` and `delete` need `write`. The Authorization decision is unchanged: it is asked with the level the operation needs. The kind is checked by the host around it: a Version declares a Resource with a kind, and an operation of one kind on a name declared or registered with the other is answered as if that name were not declared (`not-declared`) or not registered (`not-registered`), with the kind that is there in the refusal's details and its fix. A new reason was considered (`wrong-kind`) and left out: the two existing ones already say which condition failed, and `authz` keeps its interface.

### What an S3 backend must keep, and where it will differ

It keeps: the five operations and their semantics above; the key rules (checked by the host, not the backend); the bounds (5 GiB a file, 64 KiB a chunk, 1,000 a page, 10 s, the pool's and the open files' at-once); the refusals and errors and their order; the Operation log entries word for word; the byte order of `list` (S3's general purpose buckets list "lexicographically by their UTF-8 encoded byte values"; its **directory buckets do not list in order and are not supported**); the same content type it was given (S3 keeps `Content-Type` natively); seconds for the time of last change; `key-conflict` as far as a check before the put can give it. And the body shape now fits it: **a stream in and a stream out is what S3 offers — a get is a response body, a put of a body whose length is not known before it is read is a multipart upload** — so the backend interface asks of S3 only what S3 does naturally, where the one buffered call asked the program to hold a file whole in its memory.

It differs: no rename, so a put is S3's own atomic `PutObject`; strong read-after-write consistency of reads and lists is S3's since December 2020 (from knowledge, not verified this session) and must be checked for every other S3-compatible store a company brings; `key-conflict` is not atomic (above); `full` (the disk is full) never happens and quotas come from the store; a store unreachable is `unavailable`; a credential and an endpoint are needed and sealed; a `prefix` inside a bucket lets several Resources share one bucket, which makes "one Resource is not inside another" a check of prefixes at registration.

### The mount

The image keeps its read-only root filesystem and every other hardening. The Compose file gains one mount: a **bind** of the host directory `${VIBE_STORAGE_DIR:-./storage}` at `/var/lib/vibe/storage`, read-write, and `serve --storage-root /var/lib/vibe/storage`. A bind and not a named volume, because the ticket asks that the administrator see the files on the host (and back them up with the host's tools). The directory must be owned by `65532:65532` (or writable by it): with every capability dropped the program cannot write a directory another user owns (verified, below), and the install page says `sudo chown 65532:65532 storage` and `mkdir storage/<resource>` for each Resource. Docker makes the mount's target even on a read-only root (verified with `debian:13`, below). `vibe serve` with a `--storage-root` that is not there or is not a directory starts all the same and says so in its log (an installation as downloaded must come up before the administrator has made the folder), and refuses Storage registrations until it is; without the option, Storage Resources cannot be registered (`storage-not-configured`) and nothing else changes.

## Considered Options

- **Real directories in the interface** (`mkdir`, `readdir`, empty folders): closer to a file system, and no S3 backend could keep it without zero-byte "folder" objects that S3's own console makes and every other tool sees as files.
- **Keys taken as any UTF-8, normalised by the host**: friendlier, but a key read back would differ from the one written, and a hostile key would reach the disk in some form.
- **`openat2` alone**, or **canonicalising the path and comparing its prefix**: the first does not exist on macOS (the local loop); the second is the classic time-of-check-to-time-of-use hole, since a link can be planted between the check and the open.
- **Writing in place** (open, truncate, write): a reader sees half a file and a crash leaves one.
- **Temporary files beside the target** (`<folder>/.vibe-put-*`): no cross-folder rename, but leftovers anywhere in the tree, and cleaning them means walking it all. The staging folder is one place.
- **`spawn_blocking`**: no bound on its queue (rule 3).
- **Bodies inside one JSON call, as base64** (stage 1, replaced by the product owner's decision of 2026-11-22): honest about what the invoke binding alone gives, but the 8 MiB call bound, the base64 text bound, the 256 MiB budget, and the memory it cost (24 requests of 17 puts each held 1.7 GB for nine seconds, measured at the stage 1 review) were consequences of the shape, not choices; and the runtime already had the rest of the path (above, read from source).
- **A sidecar or the file name for the content type**: above.

## Consequences

- Storage is a kind beside `postgres` everywhere a kind is named: the API, the Manifest, `vibe check`, `vibe deploy`, `vibe pull`, `vibe resources`, the Dashboard, the local loop. Nothing about Storage is in the Authorization decision.
- An Application cannot tell which backend a Resource has. A Resource can be moved from a directory to S3 by copying its files and registering it again, without a new Version.
- The host holds one descriptor per Storage Resource for the program's life, beside its 4,096 open files' worth of bounds (contract, "The open files it needs"), and at most 8 more in use per operation thread while it walks; a body being read, written or sent holds one too — 16 a request, 512 the program (contract, "Storage: Bounds").
- The administrator owns backups, quotas and the disk: the platform writes durably (`fsync`) and says `full` when the disk is.
- Someone with write access to the host directory can still plant, change or remove files the Applications then read: the platform defends the Resource's boundary, not the host. What it guarantees is that nothing it reads or writes is outside the directory, and that what it writes is whole.
- A response body the host itself feeds goes on being sent after the Application's code has ended: the connection owns the sending, and a disable, a client that takes no byte for 30 seconds, a client that goes away, or the program's stop ends it early. The request's records are written when the response's head is decided, as before.
- Ranges, resumable or multipart uploads, an upload that outlives its request, appending, renaming and conditional writes are later decisions; a copy is possible (`put(k2, (await get(k1)).body)`) but is not one atomic server-side operation. A response the Application's code generates as a stream stays whole and at most 8 MiB. The Application's request body bound rises to 5 GiB and 64 KiB with this ticket, and `vibe request`'s command line stays at 1 MiB.

## Experiments run for this ADR (2026-11-21, outside the repository, under `/tmp/t85s/exp/`)

- `walk/` (Rust, `rustix` 1.1.6 and `unicode-normalization` 0.1.26 from the lock file, built offline), on Linux 6.8 and ext4: with links planted inside a directory (`etc -> /etc`, `secret -> ../outside-secret`, `other -> ../other`, `a/inner-link -> ok.txt`) and a FIFO, `openat2(BENEATH | NO_SYMLINKS | NO_MAGICLINKS | NO_XDEV)` refused every link (`ELOOP`) and `../x` and `/etc/passwd` (`EXDEV`), and allowed `a/../a/ok.txt`; the segment walk with `O_NOFOLLOW` refused every link (`ELOOP` for the last segment, `ENOTDIR` for a folder) and **did not** stop `../outside-secret` (so `..` must be refused by the key rules, as it is); both opened the FIFO at once with `O_NONBLOCK`, and `fstat` showed it was no regular file. A reader opened before `renameat` read the old content whole (`"OK"`) while the path then held the new one; `renameat` onto the link `secret` replaced the link and left `outside-secret` unchanged; `renameat2(RENAME_NOREPLACE)` onto an existing file failed `EEXIST`; opening a file as a folder failed `ENOTDIR`; `fsetxattr` / `fgetxattr` of `user.vibe.content-type` worked on a read-only descriptor; `is_nfc` was false for `cafe\u{301}` and `\u{212b}`.
- The same binary in `debian:13` under Docker 29.2.1 with `--read-only --cap-drop ALL --security-opt no-new-privileges:true` and the default seccomp profile: identical results, so `openat2` is allowed there. As user `65532:65532` on a bind-mounted directory owned by uid 1000, mode `0755`, `touch` failed `Permission denied`; the mount's target `/var/lib/vibe/storage`, absent from the image, was made by Docker on the read-only root.
- `order/order.py`: a depth-first walk with names sorted plainly gave `a/b/c, a/b-, ..., a-b` against S3's `a-b, a.b/x, a/b-, ...`; with each folder's name taken as `name/` it gave S3's order exactly, and agreed with a byte sort of whole keys on 20,000 random trees (alphabet with `-`, `.`, `0`, `/`, `é`, upper case, space).
- Not run: the image itself (distroless) with a Storage mount, a kernel without `openat2`, macOS, NFS, the heap cost of an 8 MiB body, S3.
