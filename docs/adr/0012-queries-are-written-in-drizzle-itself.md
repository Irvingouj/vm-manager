# Queries are written in Drizzle itself

Application code queries every database, its own and shared ones, with Drizzle (`drizzle-orm`), not with a look-alike of our own. The platform connects it through Drizzle's proxy driver, so each statement becomes one host operation attributed to the request in flight. An Application's own structure is authored as a Drizzle schema and its migrations are generated by `drizzle-kit`; a shared database's structure is pulled by the platform as a Drizzle schema file.

Coding agents already write Drizzle fluently, which matters more here than for a hand-written codebase: the Builder's agent is the front door (ADR 0006), and an API it knows needs no teaching. A spike showed it works in our runtime (`docs/research/drizzle-in-the-guest.md`): `drizzle-orm` 0.45.4 bundles into the single classic script the guest requires with no shims, adds about 4–5 ms to a new isolate and a few tens of microseconds per query, and returns values the way its types promise.

## Considered Options

- **A thin typed query layer of our own**: full control of the surface, including making raw SQL unreachable. Rejected because agents would have to learn it, and the spike found Drizzle no more expensive to support.
- **Raw SQL with generated row types**: simplest to build; loses the typed query building that keeps an agent's mistakes at compile time.

## Consequences

- We write the transaction support ourselves: Drizzle's proxy driver refuses transactions. The spike's version is one small class in the SDK and three host operations.
- Raw SQL is always reachable from Application code through Drizzle. Access levels are therefore enforced by the host and the database role, never by the types; a read-only type is guidance for the agent and nothing more.
- The platform pulls a shared database's structure with a privileged role and hands the result to the Builder; a weak role yields a silently incomplete definition.
- The platform applies own-database migrations itself, from the files `drizzle-kit` generated, without running `drizzle-kit` or Node on the server.
- `drizzle-kit` cannot generate a column rename without an interactive answer, and a dropped column is generated with no warning. The deploy path has to handle both; this is for Application-owned databases and migrations to settle.
- We depend on a library that is before 1.0 and whose 1.0 line was not tried.
