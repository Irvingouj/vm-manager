# A shared database's logins are sealed under the installation's key, bound to their row, and never sent to the platform database in clear

The spec (user story 16) gives Platform administrators "Resource credentials stored encrypted under a key that is not in the database, so that a database dump does not leak them". The ticket "Resources and Grants in full" asks that "a dump of the platform database contains no usable Resource credential; without the key the program says so and does not start serving that Resource". A comment on it, from the review of "An Application's own database", adds that the passwords of an own database's two roles are sent to the platform database as bind parameters, which a Postgres with statement logging writes to its server log (`docs/research/what-postgres-sees.md`, section 5). `blackbox/CONTRACT.md`, "Resources and Grants in full", is the interface this decision led to.

Status `proposed`: written on 2026-11-23 with the first stage of the ticket (what is sealed, and what the program does at start); the choices marked "chosen by the agent" are the product owner's to change. Replacing a Resource's logins is the ticket's next stage; replacing the key is not decided here ("What was considered and not taken").

What already exists and constrains it (read in this session; "code" is `crates/vibe/src`, "contract" is `blackbox/CONTRACT.md`):

- ADR 0018 already decided that **one key, given at install, seals every secret the platform keeps**: `VIBE_SECRET_KEY`, 32 random bytes in base64, in the environment of `vibe serve` and never in the platform database; AES-256-GCM under keys derived from it, one for each use; and that "the ticket on Resources in full seals Resources' credentials under the same key". It also says what a missing or other key does to the OIDC connection (not used; the program serves all the same). The code is `oidc/key.rs` and `oidc/seal.rs`: AES-256-GCM through `ring`, HKDF-SHA256 with a salt for each use, a random 96-bit nonce, the stored form `1 || nonce || ciphertext || tag`, and associated data of 32 bytes that the caller chooses (a session's cookie digest for its refresh token). `ring` is already a dependency of `vibe`; `aes-gcm`, `chacha20poly1305` and `aws-lc-rs` are not in `Cargo.lock`.
- A database Resource's connection is stored as JSON in `resources.connection` (`bytea`), through a module, `resources::sealed`, that says it is "the one place that knows the stored form (the ticket "Resources and Grants in full" encrypts it there)". An own database's role passwords are `text` columns of `own_databases` and are sent as parameters of `INSERT INTO own_databases ... VALUES ($1, $2, $3, $4)` (code: `own_db.rs`, `passwords()`; `platform_db/steps.rs`, steps 3 and 5).
- The platform's role is not a superuser (contract, "Installing"), so it cannot set `log_parameter_max_length` for itself, and an operator who keeps statement logging on elsewhere is outside the program's reach.
- The platform installs nothing in a shared database and logs in as a role the administrator supplies for each Access level (ADR 0013), so a login can only be supplied again by the administrator who has it; an own database's roles are the platform's own, and it sets their passwords itself.
- The program starts without the key (contract, "The installation's key"); Compose requires it.

## The decision

**A database Resource's whole connection is sealed, in the program, before any statement is built, with the installation's key and a use of its own.** Host, port, database, roles and passwords are one sealed value; the stored column holds nothing else. The use is a new HKDF salt (`vm: a database Resource's connection`) next to the existing four, with the existing `Sealer` and the existing stored form. No new dependency, no new key, no second place for it.

**The sealed value is bound to its row.** The associated data is a SHA-256 of a fixed label, the Resource's `id` and its name. A sealed value copied to another Resource's row does not open there, so a person with write access to the table cannot make one Resource reach another's database by moving what is stored. Ids are never reused and a Resource is never renamed, so a Resource removed and registered again does not open the old value either. The id is therefore taken before the row is written, in the same transaction, so that the value can be sealed for it.

**An own database's role passwords are sealed the same way, with a use of their own, bound to their Application's row and the column.** They are chosen and sealed in the program, so the parameters of the statements that store them are ciphertext and the platform database's server log never holds a password, with or without statement logging. The verifiers sent to an own database's own Postgres are unchanged.

**Without the key, or with a key a value does not open under, the program serves and does not serve what it cannot open.** A database Resource whose connection does not open is **unusable**: its operations fail `unavailable`, its pulls `503`, and the program's log says why at start and then at most once a minute while it lasts (`no-secret-key`, `does-not-open`, or `not-sealed` for a row still in clear though the program has the key). Its Grants, its existence and everything of other Resources are untouched, and Storage Resources, which hold no credential, do not need the key. An own database whose passwords do not open under *another* key gets new ones at its next use (the platform sets them on the roles it owns), and none is lost. Nothing that would have to be sealed is made without the key: registering a database Resource and sending an Application's first Version are refused `409` `no-secret-key`. Replacing a Resource's logins (the ticket's next stage) seals them under the key the program has and makes the Resource usable at once.

**A platform database from before this decision is sealed in place at the first start with the key**, row by row, each in a transaction of its own that holds the row by its lock from reading it to writing it (so that no statement carries a clear value to compare with), before the program says it is listening and within 15 seconds; a row another session holds is waited for a second at a time, a row not sealed in time is not served (`not-sealed`) until a later start seals it, and the program's log says how many are left. The program writes that earlier copies of the clear values remain in backups and in Postgres's old files, and that logins of shared databases should be changed at the database and replaced.

## What was considered and not taken

- **A key file named by an option, or both a file and the variable.** The variable is what Compose and the contract already require; a second place needs a rule for which wins, as ADR 0018 found for OIDC. A file option can be added later without changing what is stored.
- **Sealing the passwords only, and leaving host, port, database and roles in clear.** The logins are one value in the code already; a dump that says where every company database is, and under which role, is a map for whoever then finds a password in the environment of a program.
- **No binding to the row (sealing with no associated data, or the name only).** A ciphertext moved to another row would open there. The cost of binding is one hash.
- **Choosing a cipher crate (`aes-gcm`, `chacha20poly1305`).** `ring` is already in the program for the same purpose, and the Sealer is written and tested; rule 1 is kept by the dependency.
- **Making the key mandatory: the program refuses to start without it.** Simpler (no unusable state, no test of one), and Compose requires it already. Not taken because the ticket says the program "says so and does not start serving that Resource", and ADR 0018 says it serves all the same. The cost is a state to test and a default key in the black-box harness. If the product owner prefers it, "At start" shrinks to one start-up failure and the unusable Resource disappears.
- **Deriving an own database's passwords from the key and the Application's id, so that nothing is stored.** Nothing to seal, nothing to migrate. Not taken: it ties every own database's passwords to the key never changing (a replacement would need an `ALTER ROLE` for every own database before the program could start), and a key that is wrong would not be told apart from a missing one.
- **Telling the operator that the platform's Postgres must not log parameters, instead of sealing.** The platform cannot make that so and cannot see that it is so; the ticket's note offers it as the alternative to keeping secrets out of parameters.
- **Choosing new passwords for every own database when the old ones are sealed**, so that the clear ones in old backups no longer work. It needs an `ALTER ROLE` and a SCRAM derivation (4096 rounds) for each own database, which a start that ends within 15 seconds cannot do for many Applications. The program says old copies remain; replacing an own database's passwords on demand is not offered.
- **Sealing in a separate command (`vibe seal`) rather than at the first start.** A step an installation has to remember before its dump is safe.
- **Replacing the key.** Not decided here. Rotation by two keys at once, with a key id on every sealed value, read lazily while the program runs, is more machinery than one program needs. Not rotating at all (ADR 0018: losing the key means connecting again) leaves an administrator without a way to change the key short of supplying every Resource's logins again, and an administrator may not have them. A command run with the program stopped, which opens every sealed value with the current key and seals it again with a new one in one transaction, is the likely answer and has a ticket of its own.
- **Keeping the key in a cloud's or the machine's key store.** The platform database and its key are on the same host in most installations; a store is an installation's choice and is what a later option `--secret-key-file` or a command would read.
- **Sealing `storage_cursor_key`** (the key a Storage list's cursor is sealed with, kept in clear in the platform database): not a credential; sealing it would make Storage need the key for every `list`. Left, and said so.

## Consequences

- A dump of the platform database holds no usable Resource credential, no own database's password, and no part of where a shared database is. Whoever holds the dump and `VIBE_SECRET_KEY` holds all of them; the key sits in the program's environment, so a person who can read that and the database has everything.
- **Losing the key** means supplying every database Resource's logins again (the ticket's next stage gives the command), connecting OIDC again (ADR 0018) and that every session and tool credential ends at its next renewal; no Application's own database is lost.
- **An installation without the key cannot use a database Resource or an own database, and cannot deploy a first Version.** The Compose file requires the key; only a program started by hand is affected. The black-box harness starts its programs with a key unless a test says otherwise, and the local run keeps one of its own in `.vibe/local/secret-key`, so a Builder sets nothing.
- The program's memory holds the opened logins while a Resource's pools exist (a password is a `String` held by the pool's target); nothing is wiped on drop, so a core dump of the program holds them. Only the credential broker of ADR 0002's later split would change that.
- Old copies of the clear values stay in backups, in Postgres's write-ahead log and in dead rows. After an upgrade the administrator should change the logins at the shared databases and replace them here.
- The connections the program makes to shared databases and own databases are not encrypted in transit by this decision (the program connects with `NoTls`; read from the code). SCRAM keeps a password off the wire; rows are in clear.
- For the ticket's next stage: a Resource's pools must be replaceable while the Resource lives (replacing logins without deploying again), and a write of a Resource's row (logins, location, description, removal) follows the rule of "A write whose answer is lost" as a write of a Grant does: the row's lock first, memory forgetting the Resource's Grants and logins when the answer is lost, so that a removed write login is never used on a guess.
- The black-box tests can see all of this from outside: a dump and the server log of the platform database searched for recognisable strings, a sealed value copied between rows, a program started without and with another key.
