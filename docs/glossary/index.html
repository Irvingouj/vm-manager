An open-source, self-hosted platform on which an enterprise's employees and their AI coding agents build, deploy and run internal applications against shared, IT-governed infrastructure.

#Language

#Building blocks

Application: A stateless program, deployed by a Builder, that answers web requests and reaches enterprise infrastructure only through the SDK. It follows the Cloudflare Workers execution model without being Cloudflare-compatible. Avoid: Worker (reserved for future background compute), service, project

Manifest: The TypeScript value in an Application's project that names the Application and lists the Resources it uses. Deploy turns it into the Application's Declared access. Avoid: Config, bindings file, wrangler file

Version: One deploy of an Application, kept unchanged: its bundled code, its Declared access and the Git commit it was built from. An Application serves exactly one Version at a time, and going back means serving the previous one. Avoid: Release, build, revision, deployment (for the thing; deploy is the act)

Dashboard: The page every employee signs in to, listing the Applications they can contribute to and the Applications shared with them. The same list is available to their agent. Avoid: Portal, console (IT's admin surface), app store

Integration: Separately trusted code that exposes a few narrow business functions and reaches Resources as itself. Applications call it instead of holding privileged access. Anyone may write one; each function takes effect only once the Resource owner releases it. Avoid: Plugin, connector, external API (an outbound HTTP endpoint is a different thing)

Resource: A named piece of enterprise infrastructure that IT registers and governs, and that an Application reaches through the SDK by its logical name alone. Every signed-in employee can see that a Resource exists (its name, a description and whom to ask for access); anything more needs a Grant. Avoid: Binding (the Cloudflare and OpenWorkers term), service, backend

Resource owner: The person or Group answerable for a Resource. They, or a Platform administrator, release the Integration functions that reach it. In Milestone 1 the owner is recorded only; Grants are written by Platform administrators. Avoid: Data owner, steward, admin

Schema owner: The one party allowed to change a database's structure: the Application itself for its own database, and someone outside the Application for a shared one. Avoid: DBA, admin, maintainer

Trusted context: The platform-created value that says which User, Application and request an operation belongs to. Application code receives it and cannot construct one. Avoid: Session, token, credentials

#Authorization

Grant: A Platform administrator's statement that a Group may reach a Resource at a given access level. It names a Group, never a single User, and covers the whole Resource. It holds in every Application, and it also decides who may build against the Resource. Avoid: Permission, ACL, role

Access level: How much of a Resource a Grant opens. For a database there are three, each including the one before: structure (pull its table structure, no rows), read, and write. Avoid: Role, permission set, scope

Group: A set of Users defined in the enterprise directory and reported by the identity provider. The platform does not define its own. Grants are given to Groups. Avoid: Role, team, access list

Declared access: The list, taken from an Application's Manifest at deploy and fixed for that Version, of the Resources it uses and at what access level. Nothing outside it is reachable. Avoid: Binding, scope, app permission

Autonomous grant: A Grant that lets code reach a Resource as itself, whatever the User it is serving may access. Only an Integration can hold one on a shared Resource; an Application acts as itself only in its own database. Avoid: Service account, elevated access, bypass

#Audit

Operation log: The platform's record of every operation on a Resource: who, through which Application, what statement, how many rows, and whether it succeeded. It contains none of the Resource's data. Avoid: Audit trail (ambiguous between the two layers), access log

Change history: The record of each row that was changed in an Application's own database: old value, new value, who and through which Application. The platform keeps it in the platform database, out of reach of the database a Contributor's migrations run in (ADR 0017). Readable, through the Application, by whoever may use the Application. Avoid: Audit log, versioning, revision table

#People

Platform administrator: A member of the one directory Group named when the platform is installed. They register Resources, write Grants, see every Application and can disable any of them. The platform keeps no administrator accounts of its own. Avoid: Superuser, root, IT (when this specific role is meant)

Builder: An employee who creates and deploys an Application, normally by directing a Coding agent. Any signed-in employee may create one. Avoid: Developer, author, employee (when the building role is meant)

Contributor: A person or Group allowed to change and deploy a given Application. An Application has no owner: it belongs to the company, and what is controlled is who may contribute to it. Avoid: Owner, maintainer, author

User: An employee who signs in to a deployed Application and uses it. Avoid: End user, customer, employee (when the using role is meant)

Coding agent: An AI tool that writes Application code at a Builder's direction. Avoid: AI, bot, agent (unqualified)
